## What this is

A reproducible demonstration of how the four DORA metrics are calculated and compared with published benchmarks. The script simulates 90 days (2027-01-04 to 2027-04-03) of deployments through this repository's two-pull-request GitOps pipeline, using the assumptions listed below. Re-run with `python dora/dora_synthetic.py --seed 365` to get identical output.

## Toil-reduction recommendations

Each recommendation cites a number from the synthetic results above, ranked by the total elapsed minutes it involves across the quarter. Because the data is invented, they demonstrate the method. With real data the same script logic would rank real bottlenecks.

1. **Shorten the wait for pull request review.** Waiting for review averaged 4.2 h per change (17% of lead time). Keep pull requests small, agree a review turnaround target, and rotate a named reviewer.

2. **Automate the image-tag pull request.** Every one of the 72 deployments needed a second, mechanical pull request to change the image tag. That stage averaged 3.4 h (14% of lead time), and 5 of 7 failed deployments came from a hand-edited manifest. Have CI open the tag-change pull request after publish (or use an image-update tool) and keep the human review. Rough estimate: median lead time would fall from 20.7 h to about 17.1 h (this ignores re-queuing to business hours).

3. **Make rollback a pre-approved fast path.** 54% of recovery time was people opening and approving the revert pull request, and 32% was detecting the failure. Median recovery was 59.6 min. Consider letting a revert of the last deployment merge on green checks without a second approver (a change-control decision for leadership), and deploy the SLO burn-rate alerts to shorten detection.

4. **Prevent the most common failure: bad image tag.** 3 of 7 failed deployments (43%) had this cause, with an average recovery of 61.0 min. Add a CI check that the image tag in k8s/deployment.yaml exists in the registry (or deploy by digest), so a mistyped tag fails the pull request instead of production.

## Scenario assumptions (all invented)

- About 0.9 changes started per weekday; people act only Monday to Friday, 9:00 to 17:00.
- Median wait for pull request review: 180 min. Median time for the second (image-tag) pull request: 120 min.
- 12% of deployments fail, split across four causes; recovery is a revert pull request with expedited review.
- No changes were excluded for deploying after the window.

## Limitations

- The results follow from the assumptions above and say nothing about real performance.
- Lead time uses elapsed time and a simplified business-hours model.
- Only 7 failed deployments occurred, so the change failure rate and recovery results are fragile: one more or one fewer failure could move them across a level boundary (median recovery 59.6 min against a 60-minute Elite cutoff).
- Deployment rework rate, DORA's fifth metric, is not modeled.
- Real measurement would take deployment events from Git and GitHub Actions, and failures from incident records.
